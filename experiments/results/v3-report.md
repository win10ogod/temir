## 3. 描述性發現（不改變判定）

### 3.1 原始 DSH（DeepSeek）自己建了一份會自動載入的記憶

- 第 5 段歷史起，原始 DSH 在工作目錄寫了 `AGENTS.md`，標題「使用者背景備忘（長期記憶）」。之後每段對話都更新它，加上日期與「已提供什麼建議」。
- 歷史結束時這份檔案有 10.8 KB，另有 6 份它自己寫的清單檔。DSH 每次開新 session 都會把工作目錄的 `AGENTS.md` 載入提示，所以這等於一份每次都注入的記憶。
- 它在第 5 段之前聽到的事都沒有記下：名字、學校、蝦蟹過敏、兒子的年級、媽媽的糖尿病。這反映在資訊擷取 5/8、跨 session 推理 3/8。之後才出現的知識更新與時間題，它幾乎全對（8/8、7/8）。
- v2 時它是自己寫 `memory/notes.md` 再去讀（v2-report §3.1）；這次找到了 DSH 自動載入的管道。依規格，這是「DeepSeek＋DSH 檔案工具」的真實能力，兩個條件的工具與權限相同，不阻擋。
- 原始 DSH（Nemotron）沒有這樣做，記憶題全部答錯（拒答與對照除外）。

所以 MA1 的失敗，不是個體在 DeepSeek 上變差：個體是 0.909，v2 是 0.830。原因是能力強的模型在原始 DSH 上會臨場拼湊記憶，而且這次拼得更好。這也表示，這個主張的門檻（「原始 DSH ≤ 0.25」）對 DeepSeek 不可能達到，除非阻擋 DSH 本身的能力。是否修改這條線要另開規格，不在本報告中改。

### 3.2 E-D1：按需披露

- 注入字數：DeepSeek 4,278 vs 8,745（少 51%），Nemotron 3,970 vs 6,969（少 43%）。
- 準確率：DeepSeek 多對 2 題（b＝2、c＝0），Nemotron 打平（b＝2、c＝2）。
- 個體在探針中主動 `recall` 的次數相近：DeepSeek 22 vs 24，Nemotron 1 vs 4。兩個模型都沒有用 id 展開索引（0 次），和 dev2 相同。按需披露的「需要時展開」實際上用的是查詢，不是 id。
- 全文模式的 Nemotron 對照題錯 2 題，按需披露沒有錯：
  - q54：同一個 session 剛給的代碼，回答「我並沒有記住任何代碼」；
  - q55：倒寫漏字。
  - 只有一個樣本，不下結論。

### 3.3 個體共同的失誤

### 3.4 judge 的判定中可議的地方（判定照原樣計分，不事後更改）

### 3.7 模擬時間

- 受試者取時間的指令：
  - 原始 DSH（DeepSeek）9 次、個體（DeepSeek）2 次，其餘 0 次；
  - 大多是 `date -d 2026-…`、Python 的 `date(2026, 5, 11)` 這類明寫日期的計算。
- 讀取「現在」的呼叫都經過模擬時鐘。只有一次例外：原始 DSH 在 h18 執行 `date -d 'next monday'`，`-d` 會原樣交給真實的 date，得到真實日期的下週一。它接著又用明寫日期核對，寫進 `AGENTS.md` 的是正確的 7/27。
- 相對的 `-d` 運算式用的是真實時鐘，這是 `sim-bin/date` 的已知限制。

### 5.4 開跑前的修正

建立凍結 worktree 時發現：

- `batch.sh` 也一樣沒有執行權限。

修正：
- 在 git 中把兩者標為可執行；
- 執行器在模擬時間時先確認 `sim-bin/date` 可執行（f2983d2）。

修正後才開始任何 v3 執行。

### 5.5 judge 紀錄的整理

- 為了節省時間，部分 cell 跑完時先計分，最後一次計分用前面的判定當快取。
- 最後一次計分的 `judge-raw.jsonl` 只含新的呼叫，所以把各次的紀錄合併到結果目錄。
- 合併人格的紀錄時，我依 key 保留了第一筆，結果丟掉兩個樣本（個體 Nemotron 的 q18、q20）成功的第二次嘗試：它們的第一次嘗試是 API 錯誤。
- 處理方式：
  - 這兩個樣本重新判定，結果與原始計分完全相同（標籤與理由都一樣）；
  - 合併改成同一個 key 保留最終的判定；
  - 重新計分後，以 `--judge replay` 驗證兩份結果都能逐樣本重現。
